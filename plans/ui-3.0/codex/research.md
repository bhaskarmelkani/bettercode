## Repo Structure Snapshot
- `packages/opencode/bin/bettercode` is the launch shim that prefers source mode when available and falls back to the packaged `opencode` binary.
- `packages/opencode/src/cli/cmd/bettercode.ts` resolves the project directory, boots the OpenCode server, and spawns the Ink TUI with `BETTERCODE_URL`, `BETTERCODE_DIR`, and optional session/password env.
- `packages/tui-ink/src/index.tsx` hydrates preferences, persists theme/history/model state, and renders the Ink app; `packages/tui-ink/src/app.tsx` owns terminal sizing, global shortcuts, route switching, and overlay stacking.
- `packages/tui-ink/src/screens/SessionScreen.tsx`, `packages/tui-ink/src/components/MessageList.tsx`, `packages/tui-ink/src/components/BottomDock.tsx`, `packages/tui-ink/src/components/Composer.tsx`, and `packages/tui-ink/src/store.ts` are the main session flow.
- `packages/tui-ink/src/components/markdown/*` and `packages/tui-ink/src/components/parts/*` are the content renderers for markdown, tool calls, reasoning, and compaction.
- `packages/tui-ink/src/components/CommandPalette.tsx`, `SessionListDialog.tsx`, `ProviderDialog.tsx`, `ModelPickerDialog.tsx`, `AgentPickerDialog.tsx`, `McpDialog.tsx`, `ThemePickerDialog.tsx`, `HelpDialog.tsx`, and `DialogOverlay.tsx` are the main command surfaces.
- `packages/tui-ink/src/components/InputBar.tsx`, `ChatPane.tsx`, and `ContextPane.tsx` exist but are not wired into the live flow, which is a useful signal of architectural drift.

# 1. Executive summary
- Current overall quality: the core is already production-minded, but the surface still feels denser and more prototype-like than it should for a premium terminal agent. The shell, data flow, and command coverage are real; the visual discipline is not yet as strict as the backend plumbing.
- Biggest strengths: clean CLI-to-server-to-TUI split, delta batching in `useSDK`, stable root tree in `app.tsx`, normalized store shape, persisted preferences, serious command palette/session management, and a markdown renderer that is already better than a throwaway CLI.
- Biggest UX problems: too many chrome layers compete for attention, tool calls are visible but not yet elegantly inspectable, the composer is powerful but crowded, and long-session readability is still more “feature rich” than “calm and high-signal.”
- Biggest architecture/code problems: one broad Zustand store owns too many concerns, `MessageList` still scales with the full transcript on render, several dialogs reimplement the same list/filter/select pattern, and there are unwired legacy surfaces that suggest design drift.
- Top opportunities: collapse detail by default, simplify the composer, unify status/help chrome, make transcript rendering proportional to visible content, and extract shared panel primitives so future UI work gets easier instead of noisier.

# 3. Research findings
- Principle: explicit operating modes beat hidden permissions. Why it matters in a terminal coding agent: users need to know when the tool is reading, planning, editing, or executing before they trust a long session. Evidence or inspiration source: [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes) makes `default`, `acceptEdits`, `plan`, `auto`, and `bypassPermissions` explicit, and the [OpenAI Codex CLI docs](https://developers.openai.com/codex/cli) treat permissions and commands as first-class topics. How it applies to BetterCode: keep the current mode visible in chrome and make mode changes a deliberate, learnable action rather than a hidden shortcut.
- Principle: keyboard-first discoverability should be obvious but not noisy. Why it matters in a terminal coding agent: users should learn the app from a single help grammar, not by memorizing per-dialog quirks. Evidence or inspiration source: [Claude Code quickstart](https://code.claude.com/docs/en/quickstart) surfaces `/help`, `?`, Tab completion, and command history; [GitUI](https://github.com/gitui-org/gitui) and [LazyGit](https://github.com/jesseduffield/lazygit) both emphasize context-based help and keyboard-only flow. How it applies to BetterCode: unify `?`, `ctrl+k`, slash commands, and footer hints into one coherent keyboard vocabulary.
- Principle: progressive disclosure is the right answer for tool output. Why it matters in a terminal coding agent: tool results are evidence, not the conversation itself. Evidence or inspiration source: [Aider](https://github.com/Aider-AI/aider) makes git integration and codebase awareness central, while [Glow](https://github.com/charmbracelet/glow) shows how terminal markdown can stay readable with restraint. How it applies to BetterCode: tool rows should summarize first and reveal raw output only when expanded.
- Principle: stable regions during streaming preserve calmness. Why it matters in a terminal coding agent: jitter and layout shifts make it harder to follow fast-moving work. Evidence or inspiration source: [Ink](https://github.com/vadimdemedes/ink) is built for componentized terminal rendering and includes virtual list support; [Claude Code quickstart](https://code.claude.com/docs/en/quickstart) and [btop](https://github.com/aristocratos/btop) both show the value of stable state and responsive panes. How it applies to BetterCode: keep the transcript, chrome, and composer anchored, and let only the newest message row change while streaming.
- Principle: dense but scannable panes are the terminal idiom. Why it matters in a terminal coding agent: the product wins by compressing state without flattening meaning. Evidence or inspiration source: [GitUI](https://github.com/gitui-org/gitui), [LazyGit](https://github.com/jesseduffield/lazygit), and [btop](https://github.com/aristocratos/btop) all rely on tight panes, strong keyboard flow, and contextual hints. How it applies to BetterCode: treat transcript, context, and dock as distinct layers with different visual weights.
- Principle: large histories need virtualization or slicing. Why it matters in a terminal coding agent: long sessions are the norm, not the edge case. Evidence or inspiration source: the [Ink](https://github.com/vadimdemedes/ink) README points at `ink-virtual-list`, and GitUI’s README repeatedly emphasizes fast, responsive terminal UI. How it applies to BetterCode: transcript rendering should scale by visible rows, not by total history length.
- Principle: codebase-aware and git-aware workflows improve trust. Why it matters in a terminal coding agent: users trust systems that mirror the actual repo and git state. Evidence or inspiration source: [Aider](https://github.com/Aider-AI/aider) explicitly markets codebase mapping and git integration. How it applies to BetterCode: keep branch, diff, session, and file context legible, but never let them overpower the actual conversation.

# 4. Best-in-class design principles for BetterCode
- Product principle: BetterCode should feel like a quiet working desk, not a cockpit. Repo evidence: `SessionScreen` keeps the shell persistent and `useSDK` batches streamed deltas, which is the right foundation ([SessionScreen.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/screens/SessionScreen.tsx#L21), [useSDK.ts](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/hooks/useSDK.ts#L21)); external references: [Claude Code quickstart](https://code.claude.com/docs/en/quickstart) and [GitUI](https://github.com/gitui-org/gitui) both center uninterrupted keyboard flow and contextual help; recommendation: keep the transcript primary and make everything else subordinate to it unless explicitly requested.
- Visual principle: treat color as state, not decoration. Repo evidence: `theme.ts` already uses semantic tokens and the transcript renderers consume them widely ([theme.ts](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/theme.ts#L21), [AssistantMessage.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/AssistantMessage.tsx#L32)); external references: [Glow](https://github.com/charmbracelet/glow) and [btop](https://github.com/aristocratos/btop) show how to stay legible without visual clutter; recommendation: reduce border frequency, reserve strong color for status changes, and avoid equal-weight chrome.
- Interaction principle: one active job at a time. Repo evidence: `BottomDock` and `Composer` already multiplex prompts, mentions, slash menus, and generation state ([BottomDock.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/BottomDock.tsx#L61), [Composer.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/Composer.tsx#L28)); external references: [Claude Code permission modes](https://code.claude.com/docs/en/permission-modes) make the active mode and approval state explicit; recommendation: when generating, scrolling should be the primary secondary action and editing should be paused, while confirmations live in a dedicated dock.
- Information-architecture rule: transcript first, context second, details on demand. Repo evidence: `MessageList`, `Sidebar`, and `BottomDock` already imply those layers ([MessageList.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/MessageList.tsx#L120), [Sidebar.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/Sidebar.tsx#L18)); external references: [LazyGit](https://github.com/jesseduffield/lazygit) and [GitUI](https://github.com/gitui-org/gitui) separate overview from detail cleanly, and [Aider](https://github.com/Aider-AI/aider) keeps codebase awareness central; recommendation: keep the transcript always centered, keep the right drawer optional, and collapse tool details by default.
- Performance principle: visible work only. Repo evidence: `useSDK` batches deltas, but `MessageList` still scans the full transcript and `store.ts` still does a few global lookups ([useSDK.ts](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/hooks/useSDK.ts#L21), [MessageList.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/MessageList.tsx#L142), [store.ts](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/store.ts#L382)); external references: [Ink](https://github.com/vadimdemedes/ink) virtual lists and [GitUI](https://github.com/gitui-org/gitui) responsiveness set the terminal standard; recommendation: make render cost proportional to visible content and keep the hot path free of global scans.
- Coding principle: shared primitives, not bespoke dialogs. Repo evidence: the UI has many one-off pickers and a few unwired legacy surfaces ([CommandPalette.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/CommandPalette.tsx#L14), [SessionListDialog.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/SessionListDialog.tsx#L24), [InputBar.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/InputBar.tsx#L15)); external references: [LazyGit](https://github.com/jesseduffield/lazygit) and [GitUI](https://github.com/gitui-org/gitui) both benefit from repeated contextual patterns; recommendation: extract a panel primitive, a filter/select primitive, and a detail expander before adding more UI variants.
- Accessibility principle: never require color to read state. Repo evidence: the UI leans heavily on colored icons, pills, and borders ([Header.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/Header.tsx#L13), [StatusBar.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/StatusBar.tsx#L6)); external references: [Ink](https://github.com/vadimdemedes/ink) is text-first by nature, and the best terminal UIs pair state color with text labels and keyboard hints; recommendation: every state should have a text label, a focus marker, and a key hint.

# 5. Audit of current BetterCode UI

### Layout and information architecture
- Severity: high. What is happening today: `SessionScreen` shows header, transcript, toast stack, bottom dock, sidebar, and status bar at once, while `BottomDock` can also turn into a full-width panel host ([SessionScreen.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/screens/SessionScreen.tsx#L103), [BottomDock.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/BottomDock.tsx#L76)); why it is a problem: the hierarchy feels dense and slightly flat because too many surfaces want attention; likely root cause in code: there is no single shell primitive with explicit priority tiers; recommended fix: define one primary working area, one secondary context area, and one on-demand overlay area; files/components likely involved: `SessionScreen.tsx`, `BottomDock.tsx`, `Header.tsx`, `StatusBar.tsx`, `Sidebar.tsx`.
- Severity: low to medium. What is happening today: `HomeScreen` uses a large centered ASCII logo and centered status content ([HomeScreen.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/screens/HomeScreen.tsx#L18)); why it is a problem: it spends a lot of vertical space on branding instead of task entry, especially on shorter terminals; likely root cause in code: startup is laid out like a splash screen instead of a launcher; recommended fix: compress the home state into a compact, action-first landing view and only show the logo on wide terminals; files/components likely involved: `HomeScreen.tsx`.

### Message readability
- Severity: medium. What is happening today: assistant responses are structurally good, but they mix text, markdown, reasoning, tool calls, compaction markers, and metadata footers in one block ([AssistantMessage.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/AssistantMessage.tsx#L32), [MarkdownRenderer.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/markdown/MarkdownRenderer.tsx#L23)); why it is a problem: long replies become segmented and visually busier than they need to be; likely root cause in code: every content type gets its own strong visual treatment; recommended fix: keep text primary, reduce framing around plain prose, and reserve boxes for actual code, logs, or diffs; files/components likely involved: `AssistantMessage.tsx`, `MarkdownRenderer.tsx`, `CodeBlock.tsx`, `InlineText.tsx`.
- Severity: medium. What is happening today: the useful assistant footer metadata lives in a dim footer row only after completion or abort ([AssistantMessage.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/AssistantMessage.tsx#L46)); why it is a problem: mode, model, duration, and token count are helpful summary data but are easy to miss; likely root cause in code: metadata is treated as a trailing footnote instead of a summary scaffold; recommended fix: move key metadata into a quieter summary strip or chip row that is easier to scan at a glance; files/components likely involved: `AssistantMessage.tsx`, `StatusBar.tsx`.

### Tool call presentation
- Severity: high. What is happening today: tool calls show status, kind, title, timing, and either JSON input, truncated output, or error text in a bordered block ([ToolPart.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/parts/ToolPart.tsx#L67)); why it is a problem: tool calls are visible enough, but not yet elegant to inspect and can dominate vertical space; likely root cause in code: raw payloads are still rendered inline as part of the transcript; recommended fix: summarize each tool call in one row and move raw input/output into an expand-on-demand detail view; files/components likely involved: `ToolPart.tsx`, `MessageList.tsx`, `store.ts`.
- Severity: medium. What is happening today: completed tool outputs are capped and wrapped in a bordered box rather than rendered as a dedicated output viewer ([ToolPart.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/parts/ToolPart.tsx#L84)); why it is a problem: the UI asks the user to trust a truncated text block for inspection; likely root cause in code: the transcript renderer is doing both summarization and detail work; recommended fix: separate summary cards from raw log/diff/output viewers and keep completed tools collapsed by default; files/components likely involved: `ToolPart.tsx`, `MessageList.tsx`.

### Streaming behavior
- Severity: high. What is happening today: `useSDK` does the right thing by batching deltas and the app tree stays mounted to avoid flicker, but `MessageList` still recomputes total height and maps the full transcript on each render ([useSDK.ts](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/hooks/useSDK.ts#L21), [app.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/app.tsx#L86), [MessageList.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/MessageList.tsx#L144)); why it is a problem: long sessions will eventually feel jittery or expensive even if short sessions feel fine; likely root cause in code: the current render path still scales with transcript size; recommended fix: switch to a visible-slice or virtualized transcript model and memoize message row view models; files/components likely involved: `useSDK.ts`, `MessageList.tsx`, `scroll.test.ts`.
- Severity: medium. What is happening today: the app already has a `visibleSlice` idea in tests, but production still renders the whole transcript ([scroll.test.ts](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/test/scroll.test.ts#L9), [MessageList.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/MessageList.tsx#L236)); why it is a problem: the architecture is aware of the right pattern but has not applied it in runtime; likely root cause in code: the optimization exists as a test concept, not as the production rendering strategy; recommended fix: promote the slice logic into runtime and make the tests validate the actual implementation; files/components likely involved: `MessageList.tsx`, `scroll.test.ts`.

### Input/composer UX

- Severity: medium. What is happening today: the app shows both a spinner in the header and a spinner-like cue in the composer while generating ([Header.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/Header.tsx#L27), [Composer.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/Composer.tsx#L374)); why it is a problem: the same state is visually repeated in multiple places; likely root cause in code: generation state is represented separately in the top chrome, bottom chrome, and status line; recommended fix: pick one primary generation indicator and let the rest become passive context; files/components likely involved: `Header.tsx`, `StatusBar.tsx`, `Composer.tsx`.

### Keyboard interaction

### Visual hierarchy

### Density and whitespace
- Severity: medium. What is happening today: many panels use generous padding and framed blocks, which helps legibility but costs vertical space in small terminals ([CommandPalette.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/CommandPalette.tsx#L125), [SessionListDialog.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/SessionListDialog.tsx#L241), [PermissionPrompt.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/PermissionPrompt.tsx#L24)); why it is a problem: the app will feel roomy on a large screen but cramped on an 80x24 terminal; likely root cause in code: static padding and height assumptions are used as the default instead of density-aware rules; recommended fix: make whitespace adaptive and keep only the most important summaries expanded by default; files/components likely involved: `CommandPalette.tsx`, `SessionListDialog.tsx`, `PermissionPrompt.tsx`, `QuestionPrompt.tsx`, `BottomDock.tsx`.

# 6. Ideal target UX for BetterCode
- Starting BetterCode: launch into a calm shell that immediately tells me project, branch, session state, model, and agent status, with one obvious path to continue or start fresh. No oversized splash; no “demo” feeling. The home state should feel like a command center for work, not a welcome page.
- Reading agent responses: assistant replies should read like well-structured notes. Text is primary, code/diff/log evidence is secondary, and metadata should be small but present enough to scan quickly. Reasoning stays available, but out of the way unless I explicitly turn it on.
- Following streaming output: the transcript should stay anchored, only the newest response should animate, and the chrome should remain still. If I am at bottom, it should stick to bottom. If I scroll up, the app should clearly tell me I am detached from live output.
- Understanding tool calls: each tool call should answer four questions fast: what ran, what it was trying to do, how long it took, and whether I need to inspect the raw result. The default view should be a concise summary row, not a full raw payload.
- Inspecting detailed tool output only when needed: expanding a tool should reveal raw input/output, structured diffs, exit codes, or MCP responses in a dedicated detail card or drawer. The detail view should feel like a document viewer, not a transcript appendix.
- Entering prompts: the prompt area should feel premium and efficient. The input line should stay visually quiet, helper suggestions should float above or below it, and attachments, stash, and slash commands should feel like metadata, not competition for the cursor.
- Navigating previous content: scrollback should feel stable and reversible. I should be able to jump to the latest state, jump to a tool or message, search a transcript, and preserve per-session scroll positions without thinking about the mechanics.
- Handling confirmations, interrupts, and errors: confirmations should be focused and obvious, interrupts should immediately update the status chrome, and errors should be compact callouts with one recovery suggestion. The user should never wonder what just happened.
- Using BetterCode during long coding sessions: it should feel calm, cumulative, and resilient. The transcript grows, but the UI should not get louder. Tool noise should collapse, context should remain available, and the app should continue to feel fast after hours of use.

# 7. Recommended UI architecture
- Component boundaries: introduce a true shell split with `AppShell`, `TranscriptPane`, `DockHost`, `OverlayHost`, and `StatusChrome`; keep route switching and overlay management separate from transcript rendering.
- Layout primitives: extract reusable primitives for `Panel`, `Badge`, `KbdHint`, `FilterList`, `DialogFrame`, `SectionHeader`, `DetailExpander`, and `EmptyState` so dialogs stop reinventing the same frame.
- Message rendering pipeline: keep the SSE event stream in `useSDK`, normalize it in the store, derive a session view model in selectors, and render messages through memoized row components that only receive the data they need.
- Tool call rendering strategy: split each tool into `summary`, `details`, and `raw` modes; render one-line summaries inline in the transcript, and route large output to a dedicated viewer when expanded.
- Event/state model: keep session data normalized, keep UI state ephemeral and local where possible, and use derived selectors for visible rows, active tools, and current prompts. Preserve the global store for coordination, but stop using it as a catch-all UI bucket.
- Styling/theming strategy: reduce the theme to a small set of semantic tokens for background, surface, muted, focus, success, warning, and danger. Centralize the mapping from state to color so every new component does not invent its own chromatic grammar.
- Performance strategy: batch streaming deltas, memoize transcript rows, reverse-index tool IDs, and virtualize or slice long transcripts. Keep expensive markdown and JSON formatting off the hot render path.
- What should be generalized: filterable pickers, command/help surfaces, modal frames, status chips, empty states, and keyboard-hint footers should all be shared primitives.
- What should remain specialized: transcript rendering, composer behavior, permission/question prompts, tool detail viewers, and diff/log rendering should stay domain-specific and narrow.

bettercode · dev · session 12                    plan · sonnet · ready
───────────────────────────────────────────────────────────────────────
You: add validation to the form

  ▸ bash npm test · 42ms · exit 0

```text

[plan] [@src/app.tsx] [2 files]           ctrl+k commands · esc clear
```
- Tool call cards and rows: a one-line summary first, details second. A good pattern is `status icon + tool name + intent + duration + expand affordance`, with the raw output behind a caret.
- Collapsible details: expanded tool output should preserve the header row and show only the detail body below it, so the user never loses context while inspecting.
- Status line: use one bottom status strip for `agent | model | mode | session | hint`, and keep it textual, not decorative.
- Sticky context areas: keep project and branch in a quiet top bar, keep the right-side context drawer optional, and keep the transcript center stage.
- Inline error states: render them as compact callouts with a colored rail, a short explanation, and one next action.
- Diff and patch output: render unified diff hunks with file chips, line gutters, and foldable sections, not giant bordered boxes.
- Command output blocks: render shell output like logs, with command caption, exit status, and truncation count when needed.
- Session metadata and model/status indicators: align them into chips or a calm top bar instead of repeating the same state in several places.

### Rerender risks

- `ToolPart` still formats raw JSON and truncates output on the render path ([ToolPart.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/parts/ToolPart.tsx#L46)).
- `ThemePickerDialog` live-previewing the theme on every navigation tick is a global rerender multiplier ([ThemePickerDialog.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/ThemePickerDialog.tsx#L32)).
- `Composer` uses local timers for spinner and caret state, which is acceptable, but it still mixes many responsibilities in one component ([Composer.tsx](/Users/bhaskar.melkani/Documents/Projects/bhaskar/bettercode/packages/tui-ink/src/components/Composer.tsx#L60)).

### Code-level optimizations
- Promote the `scroll.test.ts` visible-slice idea into production and render only the visible transcript rows.
- Memoize row view models so message rendering only changes when the row data changes.
- Replace broad part scans with reverse indexes for tool IDs and session-child relationships.
- Keep theme previews local until confirmation where possible.
- Keep expensive output formatting out of the hot path, especially `JSON.stringify` and full markdown lexing on every rerender.

### Architectural changes
- Narrow the global store into coordinated slices or, at minimum, narrow selectors and derived VMs.
- Extract a single dialog/list frame and let each picker reuse it.
- Keep transcript rendering separate from summary rendering and raw detail rendering.
- Preserve the stable root tree pattern from `app.tsx`; it is one of the best current design decisions.

### Measurement ideas
- Add a `React.Profiler` around transcript and composer surfaces.
- Measure render counts per row during a 500-message and 1000-message synthetic session.
- Track delta batch size and flush frequency in `useSDK`.
- Compare transcript navigation smoothness with and without virtualization in a small terminal.
- Add a debug mode that logs render counts and row height estimates.

### Profiling approach
- Start with a long-transcript fixture and drive it through the actual SSE path.
- Compare render behavior before and after any transcript slicing or memoization change.
- Check both the happy path and the “lots of tool output” path, because the latter is what will expose the real repaint cost.

### Rules for future contributors
- Do not add a new dialog without a shared frame or a clear reason not to reuse one.
- Do not subscribe a component to the whole store when it only needs one message, one tool, or one flag.
- Do not leave raw `JSON.stringify` or unbounded markdown parsing on the hot render path if a summary will do.
- Do not remove the stable shell tree unless there is a better anti-flicker strategy.
- Do not introduce new `any` casts in core TUI surfaces unless they are immediately paired with a typed follow-up.

# 12. Production readiness checklist
- Usability: one obvious way to help, one obvious way to switch sessions, one obvious way to inspect tools, one obvious way to abort, and a composer that stays readable for hours.
- Consistency: one status vocabulary, one hint style, one border grammar, one modal frame pattern, and one keyboard story across pickers and dialogs.

- Performance: 500-plus message sessions remain usable, delta streaming stays batched, the app does not flicker on modal transitions, and render cost stays proportional to visible content.

- Maintainability: shared panel primitives exist, dead legacy surfaces are removed or archived, selectors are narrow, and the transcript pipeline is testable in isolation.
- Observability: render counts, delta flush counts, and runtime logs are easy to inspect when something feels slow or wrong.
- Extensibility: new commands appear in help/palette automatically, new dialogs reuse the same frame, and new tool renderers plug into a shared summary/details pipeline.
